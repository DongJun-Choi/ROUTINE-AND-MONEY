# 개발 컨벤션

## 1. 브랜치 전략

```text
main ── 배포 기준 브랜치 (보호 브랜치, 직접 푸시 금지)
  └── develop ── 개발 통합 브랜치 (보호 브랜치, 직접 푸시 금지)
        ├── feature/transaction-filter
        ├── feature/mail-import
        ├── fix/dashboard-chart
        ├── fix/upload-duplicate
        └── chore/build-config
```

- `main`은 배포 가능한 상태만 유지한다.
- 일반적인 기능 개발과 버그 수정은 `develop`에서 브랜치를 만든 뒤 Pull Request를 통해 `develop`으로 병합한다.
- 배포할 변경은 `develop`에서 검증한 뒤 `main`으로 Pull Request를 생성한다.
- `main`과 `develop`에는 직접 푸시하지 않는다. GitHub의 브랜치 보호 규칙을 적용한다.
- 하나의 브랜치는 하나의 기능 또는 수정 목적에 집중한다.

### 브랜치 이름

```text
{타입}/{짧은-설명}
```

- 타입
  - `feature`: 새로운 기능
  - `fix`: 버그 수정
  - `refactor`: 동작 변경 없는 구조 개선
  - `docs`: 문서 변경
  - `test`: 테스트 추가 또는 수정
  - `chore`: 설정, 의존성, 개발 환경 등 유지보수
- 이 프로젝트는 프론트엔드와 백엔드가 하나의 Next.js 애플리케이션으로 구성되어 있으므로 브랜치 이름에서 파트를 구분하지 않는다.
- 설명은 영문 소문자 kebab-case로 짧고 구체적으로 작성한다.

예시:

```text
feature/category-filter
feature/naver-mail-sync
fix/duplicate-transaction
docs/development-conventions
chore/prisma-upgrade
```

## 2. 커밋 컨벤션

Conventional Commits 형식을 사용한다.

```text
{타입}: {변경 내용}
```

사용 가능한 타입:

- `feat`: 기능 추가
- `fix`: 버그 수정
- `docs`: 문서 변경
- `refactor`: 동작 변경 없는 코드 구조 개선
- `test`: 테스트 추가 또는 수정
- `chore`: 설정, 의존성, 개발 환경 변경
- `style`: 코드 동작에 영향을 주지 않는 서식 변경
- `perf`: 성능 개선

예시:

```text
feat: 거래 내역 카테고리 필터 추가
fix: 동일한 카드 명세서가 중복 등록되는 문제 수정
docs: 로컬 실행 방법 갱신
refactor: 메일 본문 정규화 로직 분리
test: 자동 분류 규칙 예외 케이스 추가
chore: Prisma 버전 갱신
```

- 제목은 한글 명령형 또는 현재형으로 작성하고 마침표를 붙이지 않는다.
- 제목만으로 변경 내용을 이해하기 어려우면 한 줄을 띄운 뒤 본문에 변경 이유와 영향을 작성한다.
- 서로 다른 목적의 변경은 가능한 한 별도 커밋으로 나눈다.
- 비밀번호, 토큰, 실제 금융·메일 데이터는 커밋 메시지에도 포함하지 않는다.
- AI 코딩 도구가 생성한 `Co-Authored-By` 등의 서명을 커밋 메시지에 추가하지 않는다.

## 3. Pull Request

- 작업 브랜치에서 `develop`을 대상으로 Pull Request를 생성한다.
- 배포 준비 변경만 `develop`에서 `main`을 대상으로 Pull Request를 생성한다.
- PR 제목과 설명은 한글로 작성한다.
- PR 설명에는 아래 내용을 포함한다.
  - 작업 목적과 변경 내용
  - 주요 화면, API, 데이터 모델에 미치는 영향
  - 실행한 검증 명령과 결과
  - 리뷰어가 주의해서 볼 부분
  - 관련 이슈가 있다면 이슈 링크
- 최소 1명 이상의 리뷰 승인을 받은 뒤 병합한다.
- 원칙적으로 셀프 머지하지 않는다. 긴급한 수정은 팀에 변경 내용과 검증 결과를 공유한 뒤 예외적으로 진행한다.
- 병합은 Squash merge를 권장한다.
- 리뷰 중 추가한 수정도 병합 전에 다시 검증한다.

## 4. 코드 스타일

### 공통

- 새 코드는 TypeScript를 기본으로 하며 `tsconfig.json`의 strict 설정을 지킨다.
- 내부 모듈은 가능하면 `@/*` 경로 별칭을 사용한다.
- 컴포넌트와 타입은 `PascalCase`, 함수와 변수는 `camelCase`를 사용한다.
- 기존 파일의 스타일을 존중하고 작업과 무관한 포맷 변경이나 리팩터링을 섞지 않는다.
- 주석은 코드의 동작을 반복하지 않고 정책, 예외, 선택 이유를 설명할 때 사용한다.

### 프론트엔드

- 페이지와 레이아웃은 `src/app`, 재사용 가능한 UI는 `src/components`에 둔다.
- React 컴포넌트는 한 가지 책임에 집중하고, 데이터 정제나 저장 로직을 UI 안에 누적하지 않는다.
- 클라이언트 컴포넌트는 상태, 이벤트, 브라우저 API가 필요한 경우에만 사용한다.
- 로딩, 빈 데이터, 오류 상태를 함께 고려한다.

### 백엔드와 데이터

- Route Handler는 `src/app/api`, 공용 비즈니스 로직과 외부 연동은 `src/lib`에 둔다.
- API 입력값과 외부 메일·엑셀 데이터의 필수 값, 타입, 범위를 검증한다.
- API 오류는 상황에 맞는 HTTP 상태 코드와 사용자가 이해할 수 있는 메시지로 응답한다.
- 기존 API 응답 구조와 호환성을 유지한다. 공통 응답 형식 도입은 별도 변경으로 진행한다.
- 금액은 현재 데이터 모델과 동일하게 정수 단위로 처리한다.
- 날짜 처리 시 저장 기준과 화면 표시 기준, 타임존 경계를 명확히 구분한다.
- Prisma 스키마 변경은 새로운 마이그레이션과 함께 관리하며 이미 적용된 마이그레이션은 수정하지 않는다.

## 5. 검증

모든 코드 작업 후 아래 명령을 반드시 실행한다.

```bash
npm run build
```

Docker PostgreSQL 상태를 확인할 때는 다음 명령을 사용한다.

```bash
.\scripts\docker-db.ps1 config --quiet
.\scripts\docker-db.ps1 ps
```

Prisma 스키마를 변경했다면 다음 명령도 실행한다.

```bash
npx prisma validate
npx prisma generate
npm run build
```

- 변경한 화면과 API의 정상 흐름, 빈 값, 오류 흐름을 확인한다.
- 메일 동기화 테스트는 개인 메일과 환경 변수에 접근할 수 있으므로 안전한 테스트 환경에서만 실행한다.
- 검증하지 못한 항목이나 실패한 항목은 PR 설명에 원인과 함께 기록한다.
- 현재 프로젝트에 정의되지 않은 `lint` 또는 `test` 명령이 있는 것처럼 문서화하지 않는다. 관련 스크립트가 추가되면 이 문서도 함께 갱신한다.

## 6. 환경 변수와 보안

- `.env`와 실제 시크릿은 절대 커밋하지 않는다.
- 새로운 환경 변수가 필요하면 `.env.example`에 키 이름과 안전한 예시 값만 추가한다.
- 실제 비밀번호, 토큰, 데이터베이스 접속 정보는 승인된 비밀 관리 수단으로만 공유한다.
- GitHub Actions에서 사용하는 시크릿은 GitHub 저장소의 Actions secrets and variables에 등록한다.
- 로그, 이슈, PR, 문서에 실제 금융 거래나 개인 메일 내용을 노출하지 않는다.

## 7. 문서 관리

- Notion 연동 전에는 저장소의 코드와 `README.md`를 사실의 기준으로 사용한다.
- 기능 변경 시 목적, 사용자 흐름, API·데이터 모델 영향, 환경 변수, 검증 방법을 함께 갱신한다.
- Notion 연동 후에도 구현과 함께 버전 관리해야 하는 개발 규칙과 실행 방법은 저장소에 유지한다.
- 문서와 구현이 다르면 같은 작업에서 함께 수정한다.
